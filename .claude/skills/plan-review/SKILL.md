# Критика плана и правка на месте

Цель: найти в готовом плане то, что сломает работу или уже устарело, и **исправить это в самом
файле плана** — а не выдать в чат список замечаний, который никто не применит.

Отвечай на языке плана (обычно русский). Термины и имена сервисов — как в плане.

Родственный скил: `task-breakdown` создаёт план, этот — чинит. Если плана ещё нет — это задача
`task-breakdown`, не эта.

## Когда НЕ применять

- Плана нет или он на 5 строк — сначала `task-breakdown`.
- Пользователь просит **выполнить** план — выполняй, не ревьюй.
- Просят «покритикуй код» — это `/code-review`, не про план.

## Шаг 0. Взять план и обеспечить откат

1. Прочитать файл плана целиком (обычно `docs/plans/<slug>.md`). Читать **весь** файл:
   критика по фрагменту почти всегда врёт про порядок шагов и зависимости.
2. Проверить, под git ли файл: `git status --short -- <путь>`. Если да — откат бесплатный,
   можно править смело. Если нет — сделать копию в scratchpad перед первой правкой.
3. Прочитать постановку-источник, если она указана в шапке плана (транскрипт, тикет).
   **Без источника критика вырождается в вкусовщину** — по нему проверяются шаги 1 и 10.

## Шаг 1. Проход по чек-листу

Десять срезов. По каждому — либо конкретная претензия с цитатой, либо явное «чисто».
Не выдумывай замечание там, где чисто.

| # | Срез | Что искать |
|---|------|-----------|
| 1 | **Потерянные требования** | Явное требование из источника, которого нет ни в критериях приёмки, ни в шагах |
| 2 | **Раздувание объёма** | Шаги, которых никто не просил; «заодно сделаем красиво»; то, что попадает в раздел «не входит в задачу» |
| 3 | **Критерии приёмки** | Непроверяемые формулировки («работает авторизация»), критерий без шага, шаг без критерия |
| 4 | **Числа и факты** | Цены, лимиты, квоты, имена сервисов, флаги CLI, версии — проверено или взято из головы; есть ли дата проверки |
| 5 | **Развилки** | Выбор без причины; причина, которая уже неверна; более дешёвый/быстрый вариант, не рассмотренный вообще |
| 6 | **Порядок и зависимости** | Блокер не в начале; happy path end-to-end не раньше деталей; шаг не атомарный; шаг без «как проверить» |
| 7 | **Дырки в проходе насквозь** | Мысленно прогони план от нуля до демо. Где он встанет? Обычно: конфиг/env не заполнен, регион не зафиксирован, callback/redirect не совпадает, доступа нет |
| 8 | **Риски** | Вероятное и непокрытое; риск без действия («учесть это») — пустышка; риск, который на деле блокер и должен быть шагом 0 |
| 9 | **Устаревание** | Статусы `[x]` против реальности: файлы существуют? команды проходят? окружение то же? Дата в плане против сегодняшней |
| 10 | **Критерий заказчика** | Скорость против полноты: план тянет туда, куда сказал заказчик, или туда, где приятнее исполнителю |

## Шаг 2. Проверять, а не догадываться

Претензия без проверки — не претензия. По типу:

- **числа, лимиты, тарифы** — `WebFetch`/`WebSearch` по официальной странице pricing/docs.
  Никогда по памяти: облачные цены и квоты меняются. В правку идёт ссылка + дата проверки;
  если проверить не удалось — так и пиши в плане: «не проверено, уточнить в консоли»;
- **статусы `[x]`** — `Read`/`Glob` по упомянутым файлам, запуск указанной команды проверки;
- **окружение** — та же команда, что в плане (`node -v`, `aws sts get-caller-identity`);
- **имена сервисов, флаги, параметры API** — официальные доки, не аналогия.

Субагенты и параллельные workflow — только если пользователь их явно попросил.

## Шаг 3. Отсеять шум (обязательный фильтр)

Прежде чем править, по каждой претензии ответь себе: **чем я могу её опровергнуть?**
Выкидывай, если:

- претензия про стиль, формулировку, порядок абзацев — план не читают вслух;
- «а вдруг» без вероятности и без цены ошибки;
- она добавляет работу, которую заказчик прямым текстом не просил (см. срез 2 и 10);
- она делает документ длиннее, не меняя ни одного действия исполнителя.

Дальше — только выжившее, с приоритетом:

- **блокер** — план не пройдёт насквозь / потеряно явное требование / число неверно;
- **дефект** — пройдёт, но криво: непроверяемый критерий, шаг без проверки, устаревший статус;
- **улучшение** — заметно усиливает результат.

## Шаг 4. Внести правки в файл плана

`Edit` по файлу плана, точечно.

- **Блокеры и дефекты** — правим сразу, не спрашивая.
- **Улучшения, меняющие объём работы** — не вписываем молча: выносим в чат вопросом
  либо добавляем в план с меткой `[опционально]`.
- Правка — минимальная: чинит причину, не переписывает соседние разделы.
- Сохраняй структуру и разметку плана: те же заголовки, чек-боксы, таблицы.
- **Не трогай `[x]`, которые подтвердились**, и не снимай их «на всякий случай» —
  снятая галочка = повторная работа. Не подтвердилось → `[ ]` + причина одной строкой.
- Новое число — сразу с источником и датой проверки.
- План после ревью не должен стать заметно длиннее. Разрослось — значит, протащил шум.

## Шаг 5. Дописать историю ревью

В конец файла плана (создать раздел, если нет):

```markdown
## История ревью

### ДД.ММ.ГГГГ
- **[блокер]** <что было> → <что стало>
- **[дефект]** <что было> → <что стало>
- **отклонено:** <претензия> — <почему не приняли>
```

Отклонённое пиши обязательно: иначе следующее ревью придёт с тем же замечанием.
Дату бери из контекста сессии, не из головы.

## Шаг 6. Отчёт в чат

Коротко, без пересказа плана:

```
Ревью <файл>: <N> блокеров, <M> дефектов, <K> отклонено.

Блокеры
1. <претензия> (строка X) → исправлено: <как>

Дефекты
1. <претензия> → исправлено: <как>

Не стал менять
- <претензия> — <почему>

Вопросы (меняют объём работы)
1. <вопрос> — рабочее допущение: <...>
```

Ссылку на файл — обязательно. Полный текст правок в чат не дублируй.

## Правила качества

- Критика без правки — не результат. Нашёл — исправь в файле.
- Ни одной претензии без цитаты из плана и без проверки.
- «Чисто» — нормальный вывод среза. План, где не к чему прицепиться, бывает.
- Не переписывай план под свой вкус: чужой план с чужими решениями — не дефект.
- Не превращай ревью в проектирование заново. Разошлись по существу решения — вопрос в чат,
  а не тихая замена выбора в таблице «Решения».
- Пропущенное лучше лишнего: один настоящий блокер полезнее десяти замечаний по стилю.
